Trabajo grupal RA1 (CEBANC). Propuesta tecnica hipotetica: no se implementa ni se entrena ningun modelo.

1. Aplicacion hipotetica: Matriculator

Una empresa de aparcamientos quiere estudiar una aplicacion que detecte y lea matriculas en imagenes de prueba, para ahorrar tiempo al personal y reducir errores de transcripcion manual.

ElementoDescripcion
ProblemaRegistrar matriculas a mano es lento y propenso a errores.
EntradasImagen ficticia o de banco de pruebas y configuracion de camara.
Datos necesariosImagenes de prueba anotadas, sin personas identificables, y un modelo ya entrenado.
ProcesamientoValidacion del fichero, preparacion de la imagen, localizacion de la matricula (YOLO) y lectura de caracteres (OCR).
SalidaRegistro de prueba con matricula y confianza, o aviso de validacion humana.
Decision humanaUna persona revisa el resultado cuando la confianza es baja o no se detecta matricula.
Riesgos y limitesPrivacidad, retencion minima de datos y errores de lectura. Solo datos ficticios, anonimos o abiertos.

4.3 Decisiones

  • Lenguaje principal de la aplicacion: JavaScript. Es el unico que corre en el navegador sin servidor, permite subir la imagen y mostrar el resultado, y se publica como web estatica.
  • Lenguaje principal de IA: Python. Mejor puntuacion (4,90), con Ultralytics YOLO para localizar la matricula y EasyOCR o Tesseract para leerla, ambos con modelos preentrenados.
  • Por que son distintos: cada uno domina una capa distinta. JavaScript cubre la interfaz y Python el modelo; se comunican por JSON.

4.4 Lenguajes descartados para la parte de IA

  • Node.js: tiene TensorFlow.js y ONNX, pero su ecosistema de vision y OCR es mas pequeno y no hay modelos YOLO y OCR tan maduros como en Python.
  • R: muy bueno en estadistica, pero pobre en vision artificial y despliegue de modelos.
  • C++: el mayor rendimiento, pero la dificultad y el tiempo de desarrollo no compensan en una prueba con imagenes sueltas.
  • PHP: pensado para servidor web, sin ecosistema propio de IA.
  • Java: viable en entornos empresariales, pero con menos herramientas de IA y mas codigo que Python.

5. Estructura del programa

5.1 Vista visual del flujo

Resumen visual del mismo flujo: si la foto es mala se repite; si la IA esta segura la barrera se abre sola, y si duda una persona revisa y corrige antes de guardar el registro.

5.2 Flujo general (9 etapas)

flowchart TD
  A[1. La persona abre la web y elige una imagen de prueba] --> B[2. Validar fichero: tipo y tamano]
  B -->|No valido| X[Mensaje de error y volver a empezar]
  B -->|Valido| C[3. Preparar imagen: redimensionar y normalizar]
  C --> D[4. YOLO localiza la matricula]
  D -->|Sin matricula| H
  D -->|Encontrada| E[5. OCR lee los caracteres]
  E --> F[6. Calcular confianza]
  F -->|Confianza alta| G[7. Mostrar matricula y confianza]
  F -->|Confianza baja| H[8. Aviso de validacion humana]
  H --> I[9. Una persona revisa y confirma o corrige]
  G --> J[Registro de prueba]
  I --> J
  1. La persona abre la web y selecciona una imagen de prueba (entrada).
  2. La aplicacion valida el fichero (formato y tamano). Si no es valido, muestra un error.
  3. Se prepara la imagen para el modelo.
  4. El modelo de deteccion (YOLO) busca la matricula en la imagen.
  5. El OCR lee los caracteres de la zona detectada.
  6. Se calcula un porcentaje de confianza.
  7. Con confianza alta, se muestra la matricula detectada (salida).
  8. Con confianza baja o sin matricula, se genera un aviso.
  9. La revision humana comprueba la imagen y confirma o corrige antes de guardar el registro de prueba.

5.3 Antes de integrar el modelo

flowchart LR
  A[Banco de imagenes ficticias] --> B[Anotar matriculas]
  B --> C[Dividir en entrenamiento, validacion y prueba]
  C --> D[Elegir modelo preentrenado: YOLO y OCR]
  D --> E[Ajustar o configurar]
  E --> F[Evaluar: precision y errores]
  F --> G[Exportar modelo y fijar umbral de confianza]

El equipo prepara datos anotados sin personas identificables, elige modelos preentrenados, los evalua y fija el umbral de confianza a partir del cual se pide revision humana.

5.4 Despues de integrar el modelo

flowchart LR
  A[Interfaz web JavaScript] -->|imagen| B[Servicio Python]
  B --> C[Modelo YOLO]
  C --> D[OCR]
  D --> E[Matricula y confianza en JSON]
  E --> A
  A --> F{Confianza suficiente?}
  F -->|Si| G[Mostrar resultado]
  F -->|No| H[Revision humana]

Con el modelo ya disponible, la aplicacion solo carga el modelo una vez, recibe imagenes, devuelve la matricula con su confianza y deriva a una persona los casos dudosos. Se conserva lo minimo necesario y se borra la imagen tras procesarla.

6.1 Que es parsear

HTML y JSON llegan al programa como texto. Parsear es recorrer ese texto y convertirlo en una estructura que se pueda consultar: un arbol de etiquetas en el caso del HTML, y diccionarios y listas en el caso del JSON. Asi, en lugar de buscar cadenas de caracteres a mano, se pide por ejemplo "todos los titulos" o "el campo camara".

6.2 Librerias de Python

urllib y requests solo traen el texto. Quien lo interpreta es json o BeautifulSoup. El flujo siempre es el mismo: descargar, parsear, extraer y analizar.

6.3 Paso 1: descargar el contenido

Ejemplo con esta misma pagina (el index.html del repositorio) y las dos librerias de descarga:

# Con urllib (incluida en Python)
from urllib.request import urlopen

URL = "https://raw.githubusercontent.com/igorr17/trabajo-ia-matriculator/main/index.html"
html = urlopen(URL).read().decode("utf-8")

# Con requests (mas simple)
import requests

respuesta = requests.get(URL, timeout=10)  # timeout evita quedarse esperando para siempre
respuesta.raise_for_status()               # lanza un error si la descarga falla (404, 500...)
html = respuesta.text                      # el HTML como texto
print(respuesta.status_code)               # 200

Con un JSON de un servicio, requests lo parsea directamente: datos = requests.get(url).json(). Si el JSON esta en un fichero o en un texto se usa json.load o json.loads (ver el anexo del final).

6.4 Paso 2: extraer contenido con BeautifulSoup

Con el HTML descargado se construye el arbol y se buscan las etiquetas: el titulo de la pagina, el titulo de cada seccion, cuantas tablas hay y a donde apuntan los enlaces.

from bs4 import BeautifulSoup

soup = BeautifulSoup(html, "html.parser")   # texto -> arbol de etiquetas

print(soup.title.get_text())                # contenido de la etiqueta <title>

for seccion in soup.find_all("section"):    # todas las etiquetas <section>
    titulo = seccion.find("h2").get_text(strip=True)
    print(seccion["id"], "->", titulo)    # seccion["id"] lee un atributo

print("Tablas:", len(soup.find_all("table")))

# Enlaces que no son del indice interno (los que empiezan por #)
enlaces = [a["href"] for a in soup.find_all("a", href=True) if not a["href"].startswith("#")]
print("Enlaces:", enlaces)

6.6 Paso 4: analizar los datos

Una vez en un DataFrame, los datos ya no son texto de una pagina: se pueden calcular, comparar y guardar. Por ejemplo, comprobar que los totales publicados son correctos recalculando la suma ponderada y quedarse con el mejor lenguaje:

datos = df[df["Criterio"] != "TOTAL"].copy()                       # solo las filas de criterios
datos["Peso"] = datos["Peso"].str.rstrip("%").astype(float) / 100  # "30%" -> 0.30
lenguajes = cabecera[2:]                                           # columnas Python, JavaScript...
datos[lenguajes] = datos[lenguajes].astype(float)                  # "5" -> 5.0

# Suma ponderada: puntuacion x peso, sumado por lenguaje
calculado = datos[lenguajes].mul(datos["Peso"], axis=0).sum().round(2)

# Totales que aparecen en la pagina ("4,90" -> 4.90)
publicado = df[df["Criterio"] == "TOTAL"][lenguajes].iloc[0].str.replace(",", ".").astype(float)

comparacion = pd.DataFrame({"calculado": calculado, "publicado": publicado})
comparacion["coincide"] = comparacion["calculado"] == comparacion["publicado"]
print(comparacion.to_string())
print("Mejor lenguaje:", calculado.idxmax(), calculado.max())

6.7 Que mas se puede hacer con lo extraido

  • Validar: comprobar que los totales, los enlaces y las rutas de la pagina son correctos (como se hizo con la matriz).
  • Resumir: contar secciones, tablas o palabras, o generar un indice automatico a partir de los h2.
  • Comparar: descargar dos versiones de la pagina y ver que ha cambiado.
  • Reutilizar: guardar la tabla como CSV (df.to_csv) o como JSON (df.to_json) para graficos o informes.
  • Alimentar la aplicacion: en Matriculator, el mismo esquema serviria para leer los datos de entrada en JSON y para parsear el HTML de una web externa si hiciera falta.

Limite importante: requests y BeautifulSoup leen el HTML tal como lo envia el servidor y no ejecutan JavaScript. En esta pagina, los graficos de Google Trends y la tabla del apartado 2.3 se rellenan con script.js en el navegador, asi que en el HTML descargado aparecen vacios. Para esos datos hay que leer directamente los ficheros de la carpeta data/.

7. Tipo de IA y modelo

7.1 ¿La solucion es IA debil o se aproxima a IA fuerte?

Es un claro ejemplo de IA debil (o estrecha). El sistema esta disenado y entrenado exclusivamente para una tarea muy especifica: detectar y reconocer caracteres de matriculas en imagenes.

No posee conciencia, razonamiento general ni capacidad de adaptacion fuera de ese ambito de vision artificial.

7.2 ¿Usarias un modelo preentrenado o entrenarias desde cero?

Se utilizaria un modelo preentrenado, combinando una red de deteccion de objetos como YOLO para localizar la placa y un motor OCR como Tesseract o EasyOCR.

Entrenar un modelo de vision artificial desde cero requiere un coste computacional altisimo y miles de imagenes etiquetadas manualmente. Los modelos preentrenados ofrecen una precision muy elevada de base y solo requieren ajustes menores o integracion directa.
